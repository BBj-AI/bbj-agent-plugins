<objective>
Build the CI half of the example gate as one vertical slice: a stdlib-only Python test that extracts
every fenced block from both skills, enforces the fence grammar, compares the violation counts with a
committed baseline in which the two current skills are pending, and prints gate lines that
tests/run.sh already counts. The same file gets a --report mode that writes the baseline (and the
Markdown to-do list), so the baseline numbers come from the code that checks them.

Decisions implemented here: D-01, D-02, D-03, D-04 (pending list and ratchet), D-05, D-06, D-07 (fence
grammar), D-09 (stdlib only, runs in CI), D-14 (gate names carry skill, file, line), D-19 (the report
code path; the committed Markdown report is written in plan 03-04). Requirements: GATE-01, GATE-02,
GATE-06 (report mode and the machine baseline).

Purpose: from this plan on, CI rejects an untagged fence, an unknown attribute, an unclosed fence or a
`...` placeholder in a non-pending skill, and the two existing skills are listed (never silently
exempt) with counts that may only fall.

Output: tests/test_skill_examples.py (lint, pending/ratchet gates, report mode, fixtures) and
tests/skills_baseline.json (written by --report).

Open questions from research decided here (pinned by fixtures):
- Granularity of pending gates (research Open Question 2): D-01 says "a violation prints as a skip
  gate" and D-14 wants names that carry skill, file and line, so every violation gets its own gate
  (skip for a pending skill, FAIL otherwise), plus one ratchet gate per (skill, check). The research
  alternative (one skip gate per check, per-violation text outside the gate grammar) is not taken: it
  would weaken a locked decision. The skip count in SUMMARY rises now and falls to zero as Phases 4-5
  remove the skills from pending.
- Counting unit for grammar (Open Question 3): one violation per offending fence (untagged, unknown
  attribute or missing nocheck reason, disallowed tag, unclosed) plus one per bbj or should-fail block
  that contains `...` (one per block, not per occurrence). Today: bbj-programming 6 + 5 = 11,
  bbj-web-programming 1 + 4 = 5 (scanned during planning).
- D-03 when a check is not measured in a run (CI cannot re-measure live counts): the all-zero test uses
  the baseline count for that check. The rule is written here, generic over CHECKS, and used by the
  live plans.
</objective>
