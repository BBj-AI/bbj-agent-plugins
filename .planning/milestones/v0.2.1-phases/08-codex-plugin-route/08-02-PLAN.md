<objective>
Make the hook's no-route notice name the command that fits how the hook was installed (CODEX-03;
D-07, D-08, D-09). On the Codex plugin route, the enable step names
`codex plugin add bbj-local@basis-bbj`. On the installer route it keeps
`rerun install-codex.sh --with-local`. In Claude Code it keeps
`enable the bbj-local@basis-bbj plugin`. The `BBJ_HOME` / `bbjcpl` on `PATH` advice stays on both
Codex routes.

Purpose: spike 001 saw the installer wording arrive on a plugin install. Following it there would
put a second hook and a second copy of the skills on top of the plugin.

Route detection (D-07, locked): `tool_name` `apply_patch` with `CLAUDE_PLUGIN_ROOT` non-empty is the
plugin route; with the variable unset or empty it is the installer route. The installer's
`hooks.json` block stays byte-identical and gains no marker. The hooks page says Codex exports the
variable to plugin hooks, but spike 001 only saw it expanded in the command string (RESEARCH
Pitfall 2, Assumption A3). The first real-Codex step (plan 08-05 Task 1) probes the hook
environment. If the variable is absent there, D-07 cannot tell the routes apart, and replacing a
locked decision is the owner's call: plan 08-08 asks the owner in a blocking decision checkpoint
whether to amend D-07 with the documented alternative (detect the route from the script's own
location, a `.codex-plugin/plugin.json` beside `scripts/`) or to hold the phase, records the answer
in ROADMAP.md, REQUIREMENTS.md and 08-CONTEXT.md, and applies it. Plan 08-08 runs in wave 3, right
after the probe and the owner pass, before any other Linux run (08-06) or the docs (08-07).

Until 08-LINUX-RUN.md has `## Route marker`, the plugin-route wording of this plan is provisional.
This plan's SUMMARY says so in a `Provisional:` line, and plans 08-06 and 08-07 require
`## Route marker` before they start, so neither the phase nor its docs build on an unsettled
notice.
